# 晴听音乐开发指南

这份文档用于沉淀晴听音乐的开发共识，方便后续持续维护。它介绍项目现状、架构边界、开发顺序和验收标准。开始开发前还必须阅读根目录的 `AGENTS.md`。

## 1. 当前项目状态

- 当前版本：`v0.9.1`。
- 平台：Windows 10/11 64 位。
- 技术栈：Flutter。
- 产品方向：搜索优先、播放顺手、推荐克制，以个人音乐库和主动搜索为核心。
- 默认页面：我的音乐。
- 数据来源：默认通过酷狗官方接口获取，开发者管理中可配置自定义接口用于调试或兼容。
- 播放引擎：`just_audio` + `just_audio_media_kit` + `libmpv`。
- 播放策略：在线 URL 立即播放，缓存后台静默保存。
- 用户数据：优先保存在 `D:\QingTingMusic\userdata`。

## 2. 产品原则

晴听音乐不是推荐信息流产品。主要路径是：

1. 打开“我的音乐”查看收藏、歌单、专辑、歌手或云盘。
2. 在“搜索”中主动寻找歌曲、歌手或专辑。
3. 在“推荐”中打开每日推荐，或按频道和偏好开启私人 FM。
4. 从歌曲进入歌手页或专辑页继续浏览。
5. 使用底部播放器完成播放、切歌、音质、音量和队列控制。

新增功能应优先服务这条路径。推荐能力保持入口化和轻量化，不增加资讯流、榜单瀑布流或无关运营内容。

## 3. 代码结构

| 目录 | 职责 |
| --- | --- |
| `lib/controllers` | 页面状态、搜索状态、音乐库状态、播放状态 |
| `lib/data` | `MusicRepository` 接口及真实/演示数据实现 |
| `lib/models` | 歌曲、歌单、搜索实体和登录会话 |
| `lib/pages` | 我的音乐、搜索、推荐、设置和详情页面 |
| `lib/services` | API、播放、缓存、偏好、会话和日志 |
| `lib/widgets` | 可复用界面组件 |
| `lib/theme` | 全局颜色和主题 |
| `test` | 控制器、存储和 Widget 测试 |
| `scripts` | 验证、运行和打包脚本 |

关键边界：

- API 调用进入 `MusicRepository` 或 API Service，不能写在 Widget 中。
- 播放入口进入 `PlayerController`，不能让页面直接操作底层 Player。
- 本地文件进入 `AppStorageService`，不能在业务代码中自行拼接系统目录。
- 主题状态进入 `ThemeController`，不能让单个页面保存自己的主题状态。

## 4. 已完成能力

以下需求已经完成，不要重复开发：

- 歌曲播放结束后自动下一首。
- 创建歌单和收藏歌单分区显示。
- 收藏专辑与云盘歌曲按较新内容优先显示。
- 歌曲序号在悬浮时切换为播放按钮。
- 修复深色模式切换后部分设置区域透明的问题。
- 播放进度条使用完整轨道。
- Windows 播放后端切换到 libmpv，解决部分电脑卡在 `00:00` 的问题。
- 在线 URL 优先播放，音频缓存放到后台。
- 安装包支持覆盖升级和完整卸载。
- 每日推荐和私人 FM 已接入真实接口；FM 支持频道、偏好切换和自动续队。
- 播放模式支持顺序、列表循环、单曲循环和带真实历史的随机播放。
- 支持播放音质切换、播放队列、歌词页和多歌手独立跳转。
- 支持浅色、深色、预设主题色与自定义取色。
- 搜索页支持最近搜索、联想搜索和歌曲/歌单/歌手/专辑分类。

## 5. 开发策略

当前项目应使用统一的开发流程。原因很简单：晴听音乐已经有一套自己的播放状态、数据缓存、UI 风格和发版流程，频繁切换实现习惯容易出现局部功能能跑、整体体验变乱的问题。

任务按风险拆分，而不是按实现者拆分：

### 低风险体验任务

适合快速处理，每次仍然保持小提交。

- 小范围间距、颜色、悬浮和文案调整。
- 左侧导航、按钮、空状态和局部图标优化。
- 已有字段基础上的列表排序。
- 不改变数据结构的页面排版调整。
- 替换已经准备好的应用图标资源。

### 中风险功能任务

需要先读相关控制器、服务和组件，再动手。

- 播放队列、播放模式和播放错误恢复。
- 歌曲加载失败时保持上一首真实播放状态。
- 真实歌曲、歌单、专辑、歌手收藏接口。
- 歌手页、专辑页和歌单页之间的跳转与数据加载。
- 分页、懒加载、缓存刷新和跨页面状态同步。

### 高风险决策任务

开始编码前先写方案，说明接口来源、账号风险、版权风险、公开版是否启用以及失败回退。

- 变更官方接口签名、账号凭证或自定义接口回退规则。
- 私有下载功能。
- 无版权歌曲的特殊播放路径。
- 新增会改变推荐/私人 FM 队列语义的接口或播放策略。
- 后台播放、系统托盘和关闭窗口行为。
- 新增 Flutter 原生插件。

## 6. 变更优先级

1. 先保护已确认正确的播放、音乐库、搜索、推荐和导航链路。
2. UI 变更优先复用主题令牌和共享组件，并同时检查深浅模式。
3. 状态与队列变更优先补测试，再调整页面表现。
4. API 变更先用真实登录态探针证明字段和数量，再修改 mapper。
5. 涉及账号凭证、版权边界、私有下载、后台行为或原生插件时，先写方案与风险。

## 7. 标准开发流程

1. 阅读 `AGENTS.md` 和本指南。
2. 运行 `git status --short`，确认没有覆盖其他人的修改。
3. 在动手前复述目标、非目标和验收标准。
4. 只阅读与任务相关的模块。
5. 按现有分层实现，不在 Widget 中临时堆业务逻辑。
6. 为状态、解析或缓存逻辑增加针对性测试。
7. 默认运行：

```powershell
.\scripts\verify.ps1
```

8. 需要完整 UI 回归时运行：

```powershell
.\scripts\verify.ps1 -FullTests
```

如需限制全量测试等待时间，可以运行：

```powershell
.\scripts\verify.ps1 -FullTests -FullTestTimeoutSeconds 180
```

9. 只想快速检查代码时可以运行：

```powershell
.\scripts\verify.ps1 -SkipBuild
```

10. UI 任务检查 `1280x720` 和 `1536x900`。
11. 汇报修改文件、验证结果、已知风险。
12. 只有用户明确说“提交”或“推送”时才执行 Git 操作。

## 9. 注意事项

- 一个任务对应一个提交，方便回退。
- 不要同时大改 `PlayerController`、`AudioPlayerService` 和多个页面，除非任务本身就是播放架构调整。
- API、播放和本地数据变更必须在另一台干净 Windows 电脑上复测。
- 发布版本统一在本机通过脚本构建，避免不同环境生成不一致的安装包。
- 每次发布都要主动准备中文 Release Markdown。
